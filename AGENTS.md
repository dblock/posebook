# Working on Posebook

Read [CONTRIBUTING.md](CONTRIBUTING.md) and [DESIGN.md](DESIGN.md) before making changes.

## Scope and Layout

Posebook is an invitation-first Rails/Mongoid web application for recurring programs, participants, and organizers. Payments, attendee registration, and public participant directories are out of scope. Accounts, email recovery, settings, programs, scoped organizer/participant access, personal invitations, calendar booking, optional end times, dated schedule exceptions, participant applications with draft completion reminders, and retained history exist; automated booking reminders do not. Preserve that distinction in documentation.

Runtime code lives in `app/`, configuration in `config/`, request tests in `spec/requests/`, browser tests in `spec/system/`, database integration tests in `spec/integration/`, and the tested workflow display-name checker in `script/` and `spec/script/`. Ruby 4.0.9 within 4.0 and Rails 8.1 are supported; test only MongoDB 8.0 to match the deployment target. Use public Rails, Mongoid, and provider APIs. Verify and prefer current stable releases when selecting or updating dependencies while preserving compatibility.

Profile galleries store only optimized WebP images and square thumbnails in MongoDB GridFS, never the application's ephemeral local disk. There is no application photo-count cap; preserve concurrent uploads with an atomic user-document append. Validate actual JPEG/PNG/WebP content, byte size and pixel dimensions before processing. Strip metadata and preserve full-image proportions. New uploads are private; each photo has a public/private preference, overridden publicly by Private Identity and inactive accounts. Only owners and system admins modify photos; assigned organizers may view private photos for their program participants. Check authorization on every image request, including thumbnails, and prohibit browser/proxy caching so visibility changes take effect.

Venue and program galleries use separate `VenuePhoto` and `ProgramPhoto` documents and the same optimized GridFS image variants as user photos, with no application photo-count limit. Venue information, venue/program photos, and normalized venue Instagram accounts are public. Admins and venue coordinators modify venue galleries; assigned program coordinators can modify only their program's gallery. Keep image reads scoped to the requested venue/program and preserve independent user-gallery privacy. Primary-photo choices are audited, with first-remaining-photo fallback.

## Check Existing Behavior First

Many requests describe behavior that already exists. Before designing a change, search for it: read the relevant [DESIGN](DESIGN.md) section and user guide in `docs/usage/`, grep `app/` and `spec/` for the domain terms, and trace the real path from route and controller through the mutation/workflow model to any job, mailer, or worker recheck. Existing tests are the most reliable record of what is enforced; run the matching examples rather than assuming. When the behavior already exists, say so first with the enforcing code and tests, then change only what is genuinely missing, such as a gap in enforcement, tests, or documentation. Do not build a parallel flow.

Most domain behavior lives in plain models named for the operation rather than in controllers: `BookingMutation`, `OrganizerBookingMutation`, `AttendanceMutation`, `ParticipantAccessMutation` (invitations, Invite All, pauses), `ProgramScheduleMutation`, `ProgramSettingsUpdate`, `ParticipantDetailsUpdate`, `ParticipantApplicationWorkflow`, `ApplicationDraftMaintenance`, `InvitationAcceptance`, `LocationActivation`, `BookingAccess`, `ProgramRoster`, `ProgramCalendar`, `ParticipantDashboard`, `ParticipantHistory`, and `PhotoGallery`. Outbound email goes through `EmailDelivery` and `EmailDeliveryMessage`, which recheck current state before sending; recurring jobs are declared in `RecurringJobSchedule`. Account settings and deactivation live in the `AccountSettings` concern and public identity masking in `PublicProfile`. Reuse view helpers and partials listed in [UI Conventions](docs/ui-conventions.md) and test helpers in `spec/support/` instead of writing new ones.

When a request reveals that this guidance, DESIGN, or a user guide failed to point to existing behavior, update that documentation in the same change so it is not rediscovered again.

## Invariants

MongoDB is the only application database. Do not introduce Active Record, SQL-backed queues, or Redis without agreement. Active Job uses `delayed_job_mongoid` and the shared `jobs:work` worker; enqueue idempotent jobs with minimal serialized arguments, preserve transaction boundaries, and never log payloads or private exception messages. Calendar changes retain their transactional outbox. Do not enable automated participant notifications/reminders until consent, opt-outs, retry behavior, and cancellation handling exist; explicitly requested transactional account/invitation/application-status email is separate.

Use one User model with roles. Only blank-installation registration grants `system_admin`; its fixed document ID makes competing claims atomic. Normal public registration must close afterward; subsequent accounts require invitations or email-verified application registration at an active, opt-in program. Application registration uses email-bound, expiring, single-use tokens and creates only an ordinary account: never grant membership, booking access, or global roles by verifying email. Recheck program intake and account/email binding when the token is consumed, atomically with account creation and verification. Never accept role fields in public account forms. Keep password hashing and reset-token expiry/single-use behavior intact; password reset must atomically change the digest, remove the token, and invalidate all sessions. Provider messaging consent requirements apply to future participant notifications, not explicitly requested account recovery.

Every participant roster and schedule belongs to a program. Booking mutations use replica-set transactions and unique `BookingClaim` program/date and program/user indexes. Never delete or overwrite historical `Booking` dates; retain cancellation/rescheduling explanations and link replacement records. Only disposable expired/canceled claims may be removed. UTC expiry snapshots let past bookings display Completed and release claims without a background job. Store instants in UTC and calculate civil dates in the program's time zone, including daylight saving changes. Keep contacts and participant rosters private; filter email, phone, and authentication tokens from logs.

All booking, schedule-exception, and program-settings mutations share the transactional program schedule lock and reload state on retries. Preserve this write barrier so closures/time edits cannot race new bookings. Program coordinators may edit their assigned program's settings and dated exceptions, never the parent venue or sibling programs. Require short explanations; closing a booked date atomically cancels its retained booking, while time edits append an attributed change and keep the booking. Never silently delete exception history or overwrite booking time-change entries.

Only system admins activate/deactivate venues; parent venue coordinators and admins activate/deactivate programs. Inactive parents block every child without changing child flags. Keep the venue-document write barrier before the program schedule lock so deactivation cannot race new bookings. Effective inactivity blocks new bookings and date changes, not existing cancellation/attendance rights or retained history. Hide inactive public pages and image reads while retaining manager and upcoming booked-participant access. Do not replace private membership scopes with public visibility scopes.

Participant booking grants and pause/resume mutations also share that lock. A completed booking exhausts its invitation; cancellation/rescheduling preserve it. First-time participant membership grants the first cycle, never an existing participant's subsequent registration invitation. Paused participants retain bookings and cancellation rights but cannot book/reschedule. Resume does not renew a completed cycle. Keep grants and pause reasons audited and program-scoped; manager-only reasons must not reach participant pages or logs. Send invitation email only after transaction commit and report partial delivery honestly.

Assigned program/venue coordinators and system admins may edit participant account names and public display names account-wide, but not contacts, privacy, gender, roles, or booking grants through participant editing. Coordinator notes belong only to the scoped participant membership; never expose them to ordinary participants, other programs, public pages, calendar providers, or request logs. Validate and audit names and notes together in a transaction, reloading the actor and scoped membership on retries. These edits must not change schedule revisions or booking permissions.

Participant applications are program-scoped and opt-in. Pending, Not Now, and withdrawn applications grant no membership or booking rights. Verified applicants explicitly consent to scoped profile review. Only pending/Not Now consented applications extend organizer access to private profile/photos, never editing; withdrawal removes that access on every image request. Retain submission identity snapshots rather than exposing later private identity changes after withdrawal. Manager decisions require the displayed application revision and fresh authority inside a transaction; only acceptance grants participation through the existing first-cycle membership path, never renewing an existing grant or bypassing a pause. Retain every application decision and distinguish invitation acceptance in `ParticipationEvent`; never overwrite previous decisions or reveal private decision notes to applicants. Applicant withdrawal prevents later acceptance.

Application submission/decision email outboxes and ID-only jobs commit inside the workflow transaction; use `EmailDelivery.enqueue_in_transaction` with its active session, never nested transactions or SMTP. Enqueue failures must roll back admission and history. Notify active assigned program/venue coordinators once each, not every global admin. Recheck current source, audience, and application state in workers; drop withdrawn/superseded notices and never email reviewer notes. An active assigned coordinator and configured email are required before submissions can save.

Notify active assigned program/venue coordinators separately when a participant accepts a personal invitation or an application is accepted. Send one alert per person across program/venue assignments without removing the applicant's distinct decision email, even when they are also a coordinator. Admission alerts use a token-free outbox in the same transaction; an enqueue failure rolls back invitation use, new accounts, membership, and history. Preserve private invitation acceptance without configured email or an active assigned coordinator; do not claim a notification was queued in that case. Workers verify the accepted source, current participant access, active program/venue, and each recipient's current assignment; email only the participant name and an authenticated history link, never contacts, tokens, or private notes.

Admins create venues and assign `venue_coordinator` through `VenueMembership`. Venue coordinators manage their venue and inherit all its programs, including assigning `program_coordinator` through `ProgramMembership`. Program coordinators manage only assigned programs and cannot assign peers or parent roles. Participants remain program-scoped. Coordinator assignment must not expose a global user/contact directory. Program lists and private actions use `Program.visible_to` or `Program.managed_by`; never trust route or role form parameters for authorization. Public venue pages list location details and programs, and public calendars expose only active participants' public identity and consented Instagram, never private instructions, pay, contacts, booking history, invitations, or schedule explanations. Calendar access-context changes must reload the whole page to clear stale private information. Preserve unique program/user memberships and atomic grants/revocation. Revocation and deactivation retain membership/history. Participant invitations remain hashed, single-use, and consumed inside transactions.

All personal invitations accept an optional recipient email: when specified, registration and existing-account acceptance must match it; when blank, generate a private single-use bearer link without sending email. Apply the same policy to participant, venue-coordinator, and program-coordinator invitations. Wrong signed-in accounts must see a logout/account-switch action that preserves the invitation. Coordinator invitations remain scoped to exactly one venue or program. Only system admins delegate venues; only admins or the parent venue's managers delegate programs. Confirm existing-email promotions explicitly and retain other roles/booking grants. New-account creation, token consumption, and membership must commit together; reload existing recipients and recheck email and the coordinator sender's active account/delegation authority on acceptance. Never grant global roles through organizer invitations.

Use `public_name` for public calendars and announcement-facing identity; when not private, it falls back to the account name. Store only normalized `instagram_handle` values, accepting handles or profile URLs as input and deriving links for display. Registration forms default Instagram tagging on and require a handle when enabled; existing preferences remain unchanged. Users or system admins can edit this preference. Public output must use `public_instagram_url`/`public_instagram_handle`, never raw private Instagram fields. Keep the handle and tagging preference paired across concurrent saves, and keep private profile fields filtered from request logs. No public directory or announcement sender exists.

The `public_profile_private` preference overrides every public identity field: publish only "To be announced" and no Instagram, including to other participants. Keep public-sharing inputs disabled/dimmed while private without erasing saved preferences. Users and system admins can edit privacy; audit changes and preserve concurrent choices when an edit does not include that preference. Authorized managers may still identify private participants by account name in private calendar/history views. Never use disabled controls as the privacy enforcement boundary.

Venues and recurring programs use independent slugs and retained slug history under `/venues` and `/programs`. Keep scoped ID lookup and authorization; do not restore legacy root shortcuts, `/sessions` aliases, or venue-nested booking redirects. Authentication remains at `/session`. Startup creates declared indexes only; retired schema/Instagram conversions and slug backfills must not be reintroduced. Follow [Upgrading](UPGRADING.md): the sole instance must complete the conversion from PR #52 before deploying the migration-free version. Per-program terminology defaults to Program and Participant; labels are presentation-only and never change roles, booking rules, or privacy.

`mongoid-history` audits whitelisted User/Program business fields, never credentials, authentication challenges, or session secrets. Keep request actor context scoped and allow nil for anonymous/system writes. Audited email confirmation and account activation changes require fresh-document transactional saves; preserve expiry, token, and protected-admin predicates on retries. Atomic/raw updates bypass history; do not use them for normal audited field changes. No history or undo interface exists.

New programs default to Program/Participant terminology, zero pay, Monday at 09:00 UTC, and a six-month horizon. Retain explicitly configured labels, schedules, pay, and historical booking snapshots. Phone and gender are required for all accounts. Gender rules remain optional; apply the same rule checks to calendars and transactional mutations, retaining explicit organizer overrides and private explanations.

Tests use `MONGODB_TEST_URI`, never the development or production connection. The test database guard requires `posebook_test` or a `posebook_test_` prefix. Delete only records owned by a test, not entire collections or databases. Keep real network-provider calls out of tests.

Booking writes must atomically compare and increment `lock_version` with their state/history changes. Participant and organizer mutation forms submit the displayed revision; do not make missing or stale tokens default to the latest state. Preserve the originally submitted version across transaction retries and redirect conflicts to fresh program details, not a stale draft with a new token. Schedule time changes also invalidate old booking forms. Missing stored revisions are legacy zero; repeated positive confirmations may be idempotent but must never reverse a newer organizer clear.

Application drafts are owner-only and excluded from every coordinator list, review route, and application-only photo permission. Stage incomplete account fields in the draft; validate and apply only whitelisted profile fields inside the submission/history/notification transaction. Account photos use existing authorized storage outside that transaction and survive draft abandonment. Require displayed revisions for saving, submitting, and abandoning drafts; never recreate a removed draft from a stale form.

Application draft retention uses first creation, not edits: one completion reminder from seven days and cleanup from 30 days. Use the existing recurring scheduler, `maintenance` and `mailers` queues, transactional reminder marker/outbox, and current-state email checks. Cleanup must transact against submission and remove only Draft records without consent; never use a blanket application TTL or delete accounts, photos, or submitted history. Bind editor revisions to the draft ID so old forms cannot alter replacement drafts. Keep draft revisions stable when queuing a reminder so an open editor remains usable.

## Validation and Documentation

Run `bundle exec rake spec` and `bundle exec rake lint` before every development push. Run `bundle exec rake package` before committing changes to packaging, runtime dependencies, configuration, or HTTP entry points. Reuse passing results only if the tested content and configuration have not changed. The package check builds and runs the actual production Docker image and cleans up its own container and image.

For user-facing interface changes, follow [UI Conventions](docs/ui-conventions.md) and add or extend system specs in `spec/system` that exercise the real browser flows, viewports, and no-JavaScript behavior, instead of ad hoc browser scripts. Capture screenshots of meaningful states with `BROWSER_SCREENSHOTS`, including mobile layouts when affected. Embed the screenshots as GitHub-hosted attachments in the PR description and refresh them when the interface changes. Use synthetic data, keep screenshots out of the repository, and verify that the published PR contains the images rather than local file paths.

Prefer focused behavior tests while developing, followed by final validation before committing. `bundle exec rake spec` produces line and branch coverage in `coverage/index.html` and `coverage/lcov.info`. During implementation, aim for close to complete project-owned runtime coverage without trivial assertions or excluding real logic; report meaningful remaining gaps.

`bundle exec rake lint` checks Ruby, Markdown prose, embedded Ruby, spelling, and YAML workflow/job/step display names. Use Title Case for human-readable Markdown headings and workflow display names, preserving proper names, acronyms, and machine identifiers. Keep prose paragraphs on one source line. Fix Ruby offenses with `bundle exec rubocop -a` first and review corrections; if necessary, use `bundle exec rubocop --auto-gen-config` and review generated configuration rather than broadly disabling cops. Review `.spellcheck.txt` additions and fix typos instead of accepting them.

Keep `Test`, `Lint`, and `Package` workflows separate. Use only `matrix.entry` lists of compact inline objects, with no `include`, `exclude`, or separate Cartesian axes. Maintain Coveralls reporting and Ruby Danger checks. Danger runs in PR CI, not as a routine local command; inspect its actual PR result. Its changelog check currently reminds contributors about updates, not format validation.

Keep README brief: link to the hosted instance and individual user guides, and include only [Contributing](CONTRIBUTING.md) in its project-documentation section. Link operational and design details from the relevant guides. Keep DESIGN focused on current behavior, the agreed design, and still-relevant rationale, not an implementation diary. Features, improvements, and fixes require attributed changelog entries with actual PR numbers, appended above the placeholder; initial scaffolding and typo-only changes do not. Predict the number before opening a PR and verify it afterward. Add and link UPGRADING when changing released behavior incompatibly, including within `0.x`.
