# Working on Posebook

Read [CONTRIBUTING.md](CONTRIBUTING.md) and [DESIGN.md](DESIGN.md) before making changes.

## Scope and Layout

Posebook is an invitation-first Rails/Mongoid web application for recurring programs, participants, and organizers. Payments, attendee registration, and public participant directories are out of scope. Accounts, email recovery, settings, programs, scoped organizer/participant access, personal invitations, calendar booking, start times, dated schedule exceptions, and retained history exist; configurable end times and automated reminders do not. Preserve that distinction in documentation.

Runtime code lives in `app/`, configuration in `config/`, request tests in `spec/requests/`, database integration tests in `spec/integration/`, and the tested workflow display-name checker in `script/` and `spec/script/`. Ruby 4.0.9 within 4.0 and Rails 8.1 are supported; test only MongoDB 8.0 to match the deployment target. Use public Rails, Mongoid, and provider APIs. Verify and prefer current stable releases when selecting or updating dependencies while preserving compatibility.

Profile galleries store only optimized WebP images and square thumbnails in MongoDB GridFS, never the application's ephemeral local disk. Bound uploads to ten per account with a conditional single-document write; validate actual JPEG/PNG/WebP content, byte size and pixel dimensions before processing. Strip metadata and preserve full-image proportions. New uploads are private; each photo has a public/private preference, overridden publicly by Private Identity and inactive accounts. Only owners and system admins modify photos; assigned organizers may view private photos for their program participants. Check authorization on every image request, including thumbnails, and prohibit browser/proxy caching so visibility changes take effect.

Venue photos use separate `VenuePhoto` documents and the same optimized GridFS image variants as user photos, with no application photo-count limit. Venue information, photos, and normalized Instagram accounts are public; admins and that venue's coordinators modify them. Programs reference their venue rather than owning a separate gallery. Keep image reads venue-scoped and preserve the independent ten-photo cap and privacy rules for users.

## Invariants

MongoDB is the only application database. Do not introduce Active Record, SQL-backed queues, or Redis without agreement. The scaffold's in-process ActiveJob adapter is not a durable reminder scheduler. Do not enable automated participant notifications/reminders until consent, opt-outs, retry behavior, and cancellation handling exist; explicitly requested transactional account/invitation email is separate.

Use one User model with roles. Only blank-installation registration grants `system_admin`; its fixed document ID makes competing claims atomic. Public registration must close afterward; subsequent accounts require invitations. Never accept role fields in public account forms. Keep password hashing and reset-token expiry/single-use behavior intact; password reset must atomically change the digest, remove the token, and invalidate all sessions. Provider messaging consent requirements apply to future participant notifications, not explicitly requested account recovery.

Every participant roster and schedule belongs to a program. Booking mutations use replica-set transactions and unique `BookingClaim` program/date and program/user indexes. Never delete or overwrite historical `Booking` dates; retain cancellation/rescheduling explanations and link replacement records. Only disposable expired/canceled claims may be removed. UTC expiry snapshots let past bookings display Completed and release claims without a background job. Store instants in UTC and calculate civil dates in the program's time zone, including daylight saving changes. Keep contacts and participant rosters private; filter email, phone, and authentication tokens from logs.

All booking, schedule-exception, and program-settings mutations share the transactional program schedule lock and reload state on retries. Preserve this write barrier so closures/time edits cannot race new bookings. Program coordinators may edit their assigned program's settings and dated exceptions, never the parent venue or sibling programs. Require short explanations; closing a booked date atomically cancels its retained booking, while time edits append an attributed change and keep the booking. Never silently delete exception history or overwrite booking time-change entries.

Participant booking grants and pause/resume mutations also share that lock. A completed booking exhausts its invitation; cancellation/rescheduling preserve it. First-time participant membership grants the first cycle, never an existing participant's subsequent registration invitation. Paused participants retain bookings and cancellation rights but cannot book/reschedule. Resume does not renew a completed cycle. Keep grants and pause reasons audited and program-scoped; manager-only reasons must not reach participant pages or logs. Send invitation email only after transaction commit and report partial delivery honestly.

Admins create venues and assign `venue_coordinator` through `VenueMembership`. Venue coordinators manage their venue and inherit all its programs, including assigning `program_coordinator` through `ProgramMembership`. Program coordinators manage only assigned programs and cannot assign peers or parent roles. Participants remain program-scoped. Coordinator assignment must not expose a global user/contact directory. Program lists and private actions use `Program.visible_to` or `Program.managed_by`; never trust route or role form parameters for authorization. Public venue pages list location details and programs, and public calendars expose only active participants' public identity and consented Instagram, never private instructions, pay, contacts, booking history, invitations, or schedule explanations. Calendar access-context changes must reload the whole page to clear stale private information. Preserve unique program/user memberships and atomic grants/revocation. Revocation and deactivation retain membership/history. Participant invitations remain hashed, single-use, and consumed inside transactions.

Coordinator invitations are email-bound and scoped to exactly one venue or program. Only system admins delegate venues; only admins or the parent venue's managers delegate programs. Confirm existing-email promotions explicitly and retain other roles/booking grants. New-account creation, token consumption, and coordinator membership must commit together; recheck recipient email and the sender's active account/delegation authority on acceptance. Do not change participant invitation recipient policy or grant global roles through organizer invitations.

Use `public_name` for public calendars and announcement-facing identity; when not private, it falls back to the account name. Store only normalized `instagram_handle` values, accepting handles or profile URLs as input and deriving links for display. Instagram tagging is a preference, off by default, editable by the user or a system admin. Public output must use `public_instagram_url`/`public_instagram_handle`, never raw private Instagram fields. Keep the handle and tagging preference paired across concurrent saves, and keep private profile fields filtered from request logs. No public directory or announcement sender exists.

The `public_profile_private` preference overrides every public identity field: publish only "To be announced" and no Instagram, including to other participants. Keep public-sharing inputs disabled/dimmed while private without erasing saved preferences. Users and system admins can edit privacy; audit changes and preserve concurrent choices when an edit does not include that preference. Authorized managers may still identify private participants by account name in private calendar/history views. Never use disabled controls as the privacy enforcement boundary.

Venues and recurring programs use independent slugs and retained slug history under `/venues` and `/sessions`. Keep scoped ID lookup and authorization; do not restore legacy root shortcuts or venue-nested booking redirects. Startup creates declared indexes only; retired schema/Instagram conversions and slug backfills must not be reintroduced. Follow [Upgrading](UPGRADING.md): the sole instance must complete the conversion from PR #52 before deploying the migration-free version. Per-program terminology defaults to Program and Participant; labels are presentation-only and never change roles, booking rules, or privacy.

`mongoid-history` audits whitelisted User/Program business fields, never credentials, authentication challenges, or session secrets. Keep request actor context scoped and allow nil for anonymous/system writes. Audited email confirmation and account activation changes require fresh-document transactional saves; preserve expiry, token, and protected-admin predicates on retries. Atomic/raw updates bypass history; do not use them for normal audited field changes. No history or undo interface exists.

New programs default to Program/Participant terminology, zero pay, Monday at 09:00 UTC, and a six-month horizon. Retain explicitly configured labels, schedules, pay, and historical booking snapshots. Gender is optional unless the program enables consecutive-gender rules; apply the same rule checks to calendars and transactional mutations, retaining explicit organizer overrides and private explanations.

Tests use `MONGODB_TEST_URI`, never the development or production connection. The test database guard requires `posebook_test` or a `posebook_test_` prefix. Delete only records owned by a test, not entire collections or databases. Keep real network-provider calls out of tests.

Booking writes must atomically compare and increment `lock_version` with their state/history changes. Participant and organizer mutation forms submit the displayed revision; do not make missing or stale tokens default to the latest state. Preserve the originally submitted version across transaction retries and redirect conflicts to fresh program details, not a stale draft with a new token. Schedule time changes also invalidate old booking forms. Missing stored revisions are legacy zero; repeated positive confirmations may be idempotent but must never reverse a newer organizer clear.

## Validation and Documentation

Run `bundle exec rake spec` and `bundle exec rake lint` before every development push. Run `bundle exec rake package` before committing changes to packaging, runtime dependencies, configuration, or HTTP entry points. Reuse passing results only if the tested content and configuration have not changed. The package check builds and runs the actual production Docker image and cleans up its own container and image.

For user-facing interface changes, verify the real browser flows and capture screenshots of meaningful states, including mobile layouts when affected. Embed the screenshots as GitHub-hosted attachments in the PR description and refresh them when the interface changes. Use synthetic data, keep local captures and browser scripts out of the repository, and verify that the published PR contains the images rather than local file paths.

Prefer focused behavior tests while developing, followed by final validation before committing. `bundle exec rake spec` produces line and branch coverage in `coverage/index.html` and `coverage/lcov.info`. During implementation, aim for close to complete project-owned runtime coverage without trivial assertions or excluding real logic; report meaningful remaining gaps.

`bundle exec rake lint` checks Ruby, Markdown prose, embedded Ruby, spelling, and YAML workflow/job/step display names. Use Title Case for human-readable Markdown headings and workflow display names, preserving proper names, acronyms, and machine identifiers. Keep prose paragraphs on one source line. Fix Ruby offenses with `bundle exec rubocop -a` first and review corrections; if necessary, use `bundle exec rubocop --auto-gen-config` and review generated configuration rather than broadly disabling cops. Review `.spellcheck.txt` additions and fix typos instead of accepting them.

Keep `Test`, `Lint`, and `Package` workflows separate. Use only `matrix.entry` lists of compact inline objects, with no `include`, `exclude`, or separate Cartesian axes. Maintain Coveralls reporting and Ruby Danger checks. Danger runs in PR CI, not as a routine local command; inspect its actual PR result. Its changelog check currently reminds contributors about updates, not format validation.

Keep README brief: link to the hosted instance and individual user guides, and include only [Contributing](CONTRIBUTING.md) in its project-documentation section. Link operational and design details from the relevant guides. Keep DESIGN focused on current behavior, the agreed design, and still-relevant rationale, not an implementation diary. Features, improvements, and fixes require attributed changelog entries with actual PR numbers, appended above the placeholder; initial scaffolding and typo-only changes do not. Predict the number before opening a PR and verify it afterward. Add and link UPGRADING when changing released behavior incompatibly, including within `0.x`.
