# Design

## Purpose and Current Status

`Venue` represents the physical location and its public information, photos, and Instagram. A venue has multiple recurring `Program` records, each with its own weekdays/start time, time zone, pay, private instructions, booking rules, participant roster, invitations, and calendar. `Booking` represents one dated reservation; this is not a separate dated-event resource. Participants are users with the program-scoped `participant` membership role, while `program_coordinator` grants organizer access. Authentication sessions remain separate from `Program`.

Each program has audited, editable singular `program_label` and `participant_label` settings, defaulting to Program and Participant. Labels apply to its settings, calendar, roster, booking controls, invitations, and messages; Pay is fixed. Labels affect presentation only: changing them never changes roles, booking limits, gender requirements, invitation cycles, or privacy. There are no presets, venue defaults, attendee reservations, or configurable capacity rules.

Deployment startup creates declared MongoDB indexes before serving requests. Historical schema conversions, venue splits, Instagram data conversion, and slug backfills have been retired; only the current schema is supported. The sole instance must complete the conversion supplied by PR #52 before deploying this version. Normal saves generate and retain slugs; normal profile input still accepts Instagram handles or URLs. No startup data rewrites or migration flags remain.

Global admins manage everything and assign venue coordinators. Venue coordinators edit their location, create/manage every program there, and assign program coordinators. Program coordinators manage settings, participants, invitations, and bookings only for assigned programs, without assigning peers or parent roles. Participants have independent access and one upcoming booking per program, with no additional cross-program conflict constraint. Public locations and calendars never grant private access.

Posebook coordinates invitation-first participant registration and scheduling across recurring programs. Programs specialize their presentation through configurable labels without introducing domain-specific account types.

The application currently provides first-user registration, role-bearing user accounts, email/password login, email password recovery, account settings, deactivation/reactivation, program configuration, scoped organizer/participant access, personal participant invitations, calendar booking with saved times and dated schedule exceptions, retained booking history, and a Rails `/up` liveness endpoint. `/up` proves application boot, not MongoDB connectivity. Automated reminders are not implemented yet.

The shared header pairs a serif Posebook wordmark with an original AI-generated sanguine portrait supplied by @dblock: a tightly cropped woman's face with natural proportions and detailed pencil shading. Transparent PNG assets supply the 64-pixel-square header image and a separate 64-pixel-square favicon through the local asset pipeline. The visible wordmark names the home link, and the image is decorative for screen readers. No external font or image service is required.

The artwork is covered by the project's MIT license. Preserve the supplied raster unchanged in `artwork/posebook-logo-source.png`; it is not made of editable vector paths. The source contains neutral checkerboard pixels as well as transparency. Display assets recover the pencil strokes from their red-versus-blue color difference and render them as translucent sanguine ink, removing the checkerboard without filling the portrait's highlights. Regenerate the display assets with ImageMagick:

```sh
magick artwork/posebook-logo-source.png -channel A -fx 'a*max(0,min(1,(r-b-0.008)/0.42))' +channel -channel RGB -fill '#a34c33' -colorize 100 +channel -resize 256x256 -strip app/assets/images/posebook-logo.png
magick app/assets/images/posebook-logo.png -resize 64x64 -gravity center -background none -extent 64x64 -strip app/assets/images/posebook-favicon.png
```

Inspect the full portrait, the header at its actual size, and the favicon at 16 and 32 pixels after artwork changes. Keep source artwork outside the public asset pipeline.

The interface uses the official daisyUI 5.8.0 Caramellatte theme, with cream surfaces, earthy brown text, rounded fields, serif headings, and sanguine primary controls matching the logo. Its MIT-licensed theme CSS is stored locally with its license and source URL; semantic application styles use those variables without a Tailwind compiler, Node dependency, runtime CDN, or external fonts. The theme stays light regardless of the device's dark-mode preference. Calendars retain their existing pale-green/darker-green/gray meaning. Calendars and wide tables scroll inside labeled, keyboard-accessible regions on narrow screens rather than breaking status words into tiny columns.

Program pages share venue/program breadcrumbs and tab-like navigation. Public visitors can open the program view and calendar; members can also open their booking history, managers can open the participant roster and invitations, and venue coordinators can manage program coordinators. Those links do not grant access: each destination retains its server-side scope. Booking links and schedule changes return to the calendar, and pending participant invitations have a compact revoke action beside their status.

Displayed states share compact, single-word status labels: green for positive states, sanguine for canceled/revoked/inactive states, amber for pending/paused/attention states, and warm cream for neutral states. Booking, calendar, invitation, roster, account, schedule, and photo-visibility displays use the same helper and styles. Each booking presentation has one label: Canceled or Rescheduled takes precedence, then Completed for an expired reservation, otherwise Confirmed for acknowledged attendance or Unconfirmed. Private overdue follow-up remains plain text, not a second label. Roster rows show one booking/access label, with retained bookings described as plain text for paused/inactive participants. Access labels use Invited or Uninvited; Inactive, Pending, and Regular labels keep longer explanations outside the badge. Color never replaces visible status text; retained audit explanations and form options remain ordinary text.

Roster pages batch booking and completion/grant history for only the displayed memberships, using request-local read snapshots rather than per-row queries. Mutation services continue to check current database state inside their existing transactions. Venue photos load once per rendered page. Calendar navigation requests send their current access context; only a match against the server's freshly authorized context returns a calendar fragment. Changed roles, accounts, schedule revisions, or attendance windows return the full page so the browser replaces stale private controls and summaries. The response varies by the context header; no shared cache of private HTML or booking permission is introduced.

Compact Copy controls accompany private invitation links, displayed account/contact details, Instagram handles, venue addresses, and canonical venue/program sharing links. Invitation buttons sit inside their read-only link fields. Successful buttons display Copied for three seconds before reverting to Copy, with screen-reader confirmation; failures show manual-copy instructions. Copy only information already authorized for that page; never recover single-use invitation tokens or include invitation/access query parameters in public sharing URLs. Use the browser clipboard API with a selection-based fallback when it is unavailable. Controls are hidden without JavaScript, leaving the original text, contact links, and read-only invitation fields available for manual copying. Delegated clicks and newly inserted calendar controls work without inline scripts or external services.

## Google Calendar Synchronization

Optional Google OAuth connects a private calendar per program. Only booked slots are mirrored, with the model's private contact details and effective Instagram tagging preferences; invitations go to the model and authorized program/venue organizers. Rescheduling moves the original event, organizer replacements update its model, schedule edits update saved times, and cancellations cancel the Google event. Google changes never write to Posebook. Missing session end times use a one-hour Google-only duration. Default Google reminders and guest modification/invitation permissions are disabled.

The official Google Calendar Ruby client manages provider calls outside booking transactions. A calendar-specific MongoDB outbox is updated inside those transactions, coalesces each booking replacement chain, uses deterministic Google event IDs, leases worker claims, and retries errors without retaining private response text. A separate worker reconciles upcoming bookings every five minutes and skips unchanged payloads. It is not a general-purpose delayed-job queue. Refresh tokens are encrypted with the application secret, never audited or displayed. OAuth callbacks bind single-use expiring state to the signed-in manager and recheck program scope. Connecting organizers must retain active management access. Disconnect clears credentials without deleting external events. See [Google Calendar Setup](docs/google-calendar.md).

## Accounts and Recovery

There is one `User` model, not a separate admin account type. A blank installation allows anyone to register the first user without an installation secret, as explicitly requested. That account receives `system_admin` in its global roles. Public registration closes once any user exists; subsequent accounts require a personal program invitation. A fixed bootstrap document ID uses MongoDB's built-in unique `_id` constraint to prevent two concurrent first-user claims, without requiring a transaction or replica set.

Use email/password authentication initially, with BCrypt password hashing, a 12-character minimum, and the library's 72-byte maximum. Passwordless access is deferred. Public forms never accept role assignment. Sessions use encrypted, HTTP-only, same-site cookies, rotate on login/logout, and include a per-user session version. Ordinary sessions last seven days. Sign-in offers an unchecked "Remember me" choice for trusted devices: a separate encrypted credential has no application deadline and restores a fresh session after the ordinary session expires. Its browser cookie requests twenty years of storage, renewed on visits; browsers may cap that lifetime or clear storage, so literal forever persistence cannot be guaranteed. Encryption metadata deliberately has no expiry; browser storage expiry is applied separately using public cookie APIs. The credential contains only the account ID and current session version, never a password.

Failed login never grants a remembered credential. Logout or an unchecked sign-in clears it. Password changes revoke every older session/remembered credential and clear the current browser's remembered choice, retaining only an ordinary seven-day session there. Confirmed email changes, immediate administrator email changes, password resets, and account deactivation revoke remembered credentials through the same account/session checks. Merely requesting an unconfirmed email change does not revoke them. Existing-account invitation acceptance preserves the choice while rotating the session; new registrations use the ordinary lifetime. Credentials are checked against active account state on every restoration, and cookie protections remain HTTP-only, same-site, and restricted to HTTPS in production.

Email recovery links use random tokens, store only their SHA-256 digests, expire after 30 minutes, and are consumed atomically with the password update. Resetting rotates the session version, invalidating every existing session. A newer reset request supersedes older links. Requests use the same success message for known and unknown emails. Login, signup, and reset requests use Rails rate limits backed by the application's cache; these limits are per process with the current memory cache, not distributed across instances.

Account settings allow name and required phone changes. Phone input accepts spaces, parentheses, periods, and dashes, with optional `+` or `00` for country codes; ten-digit numbers without a country code are treated as US/Canada. Numbers are stored with a leading `+` and digits only. Phone numbers are unverified and cannot be used for recovery or messaging yet. Email changes require the current password and a single-use, 30-minute verification link at the new address. GET displays confirmation without changing the address; an atomic PATCH consumes the token, changes email under its unique index, invalidates all sessions, and clears authentication challenges. Until then, login and recovery use the old email. Authenticated password changes require the current password, rotate session versions, retain the current browser, and invalidate other sessions and outstanding challenges.

The profile is a read-only account summary with links to separate profile-edit, password-change, and account-deactivation pages. Successful profile/password edits redirect back to the summary with a confirmation; invalid submissions stay on their corresponding form. Every form has a cancel link to the summary. Successful deactivation signs out the user and confirms the result on the sign-in page rather than returning to an authenticated page.

Registration and profile editing collect an optional public display name, an Instagram handle, and a tagging preference. First-user and invitation registration forms default tagging on; a valid handle is required whenever it is selected. Existing opt-outs remain unchanged. For a new private profile whose disabled sharing fields are not submitted, tagging remains off until explicitly enabled. `public_name` falls back to the account name when the display name is blank; forms explain that either will be public in announcements and session calendars. Handle and profile-URL inputs normalize to lowercase handles without `@`; only `instagram_handle` is stored. Other hosts, content URLs, credentials, and nonstandard ports are rejected. Display uses `@handle` and derived HTTPS profile links. `public_instagram_url` and `public_instagram_handle` return nothing when tagging is off or the profile is private. System admins can edit display names, handles, tagging, and privacy preferences. Changing a handle preserves the selected tagging preference; concurrent saves keep the chosen handle and tagging setting together. Preferences are global across sessions, do not verify Instagram ownership, and do not add announcements or a public directory.

Users may choose `public_profile_private` during registration or profile editing, and system admins may edit it too. It defaults off to preserve existing public preferences. When private, `public_name` returns "To be announced" and both public Instagram helpers return nothing, regardless of saved display-name/tagging choices. The global switch applies at every program and hides identity from guests and other participants, not authorized program managers. Managers retain the account name in their private calendar and booking history. Native disabled fieldsets and a small JavaScript enhancement disable/dim sharing controls without erasing stored values; turning privacy off restores those preferences. The server enforces privacy independently of disabled controls. Edits that omit the preference preserve concurrent privacy changes.

Each account has a photo gallery with at most ten photos, stored in the same MongoDB database using `mongoid-grid_fs`. Owners and system admins upload, delete, and independently mark each photo Public or Private; new uploads are private. Assigned program organizers may view their participants' private photos but cannot change them. Public galleries expose only selected public photos and the current public name; Private Identity or account inactivity hides the gallery and every image publicly without erasing sharing preferences. Calendar participant names link to available galleries, and the private participant roster links organizers to photos. No public participant directory exists.

Uploads accept actual JPEG, PNG, or WebP content up to 10 MB and 40 megapixels. libvips corrects orientation, strips metadata, and creates a full-proportion WebP image bounded to 1600 pixels plus a 400-pixel square thumbnail. Original uploads are not retained. Account profiles show existing photos with their visibility labels. Square thumbnails throughout account, participant, and venue galleries open the full image in a shared modal dialog, with keyboard focus containment and Close, Escape, or backdrop dismissal. Closing clears the displayed image; failed image reads show an unavailable message. Without JavaScript, links open the image in the same tab. All image requests, including thumbnails, check current authorization and prohibit browser/proxy caching. A conditional user-document update enforces ten photos across simultaneous uploads; rejected/failed uploads clean up their GridFS files, and deletion removes both variants. Account deactivation retains private photo storage. Include the `photos.files` and `photos.chunks` collections in database backups; no persistent local disk or additional storage credentials are needed.

Accounts require a private gender selection of male, female, or other, editable during registration, in the profile, or by a system admin. The one-time migration fills missing genders with male and missing phone numbers with a fictional placeholder; see [Upgrading](UPGRADING.md). Existing reservations, cancellation, and attendance controls remain available. Gender is audited and filtered from request logs, never shown on public pages or other participants' calendars. Organizer booking selectors show gender only when the program has gender rules.

Booking rules implement `evaluate(date, user)`: return `nil` when allowed, otherwise an immutable `BookingRuleDecision` with a stable symbolic `code`, localized `message`, and boolean `overridable`. The gender rule reports `gender_required`, which cannot be overridden, and `gender_restricted`, which permits organizer overrides. Calendars show rule-blocked dates without displaying the gender rule; participant mutations reject every decision, while organizer mutations require the rule's permission and explicit consent with a retained explanation. The rule owns that policy, not consumers inspecting profile fields or message text. Booking mutations still evaluate rules inside the shared schedule transaction. This contract introduces no rule registry, executable expressions, new settings, or stored-schema changes.

Deactivation retains the user and history while revoking sessions, email-change links, and recovery links. Inactive users cannot log in or request recovery; old documents without an active flag remain active. Only system admins can manage other users or reactivate accounts. System admin accounts cannot be deactivated until global role transfer exists: protecting these accounts atomically avoids concurrent last-admin races. Public registration remains closed even if all non-admin accounts are inactive.

Development emails are written to `tmp/mail`; tests use the in-memory mail adapter. Production account email uses configurable SMTP, requires `SMTP_ADDRESS` and `MAIL_FROM`, and reports unavailable delivery rather than pretending to send email. Links use configured mailer hosts, not incoming request hosts. Phone recovery remains future work.

System admins can edit any existing user's name, email, and phone, including inactive accounts, without changing roles, passwords, or active status. Successful edits return to the user list with confirmation; invalid edits stay on the form. Admin email changes apply immediately without verification or the target user's password, clear previous verification, revoke all sessions and outstanding authentication challenges, and handle competing unique email claims. Name/phone-only edits preserve sessions and pending email changes. An admin changing their own email is signed out with confirmation and must sign in again. Account access still has separate explicit controls; missing edits or invalid access values never default to deactivation.

## Venue Photos and Instagram

Venues publish an optional normalized Instagram account and public photos, shared by their programs. Admins and venue coordinators edit them; program coordinators cannot modify location information or photos. There is no venue photo-count cap: each photo has a separate `venue_photos` document. Processing, GridFS storage, public thumbnails, deletion, and no-cache image responses are unchanged. User galleries retain their ten-photo limit and privacy rules.

The venue Instagram handle is audited with other venue settings. Photo metadata and image bytes are not part of the user/venue/program field audit; failed uploads remove their temporary GridFS files.

## User and Program Audit History

`mongoid-history` stores user and session audit entries in `history_trackers`, including original/modified values, action, version, timestamps, and an optional user modifier. User fields are limited to name, email, phone, display name, Instagram handle/tagging preference, public-identity privacy, global roles, active status, and email verification time. Session history covers name, custom/generated slugs, time zone, start time, participant pay, instructions, booking horizon, and available weekdays. Dated schedule exceptions also retain their configuration changes through the gem. Authentication secrets and challenges, including pending email addresses, password digests, tokens, expiry fields, and session versions, are never tracked.

The authenticated request user supplies the actor; anonymous registration and system/console writes have no actor unless explicitly wrapped in `Current.set(user: actor)`. Actor context is restored after each request and cleared on subsequent system writes. History begins with new writes; existing records receive no fabricated historical baseline. Storage only is implemented: there are no history pages or undo/redo routes.

Email confirmation, deactivation, and reactivation use fresh-document saves inside retrying replica-set transactions, committing the audited change and its history together. Token expiry/single-use and protected-admin predicates are checked again inside each attempt. Password-only operations retain their atomic credential updates without creating history. Other saves use the gem's normal callback semantics, including cleanup after failed persistence; this is not a database-wide audit log. Raw driver writes and atomic updates bypass callbacks and history. Maintenance scripts must use ordinary saves and explicit actor context when audit entries are required.

## Agreed Participant Workflow

An organizer first connects with a participant by email, Instagram, or text. The organizer adds them to the appropriate program, possibly with only a name or social handle, then sends a private registration link by email or through the existing conversation.

The participant invitation flow collects name, email, phone, gender, and password. Personal invitations do not prove ownership of the chosen email address; phone numbers remain unverified. Contact verification and explicit SMS consent must precede any future automated SMS. Declining SMS must not prevent registration or booking.

After accepting an invitation, the participant chooses an available day at the inviting program. The invitation has no preselected date; selection immediately confirms the booking. Participants can cancel or reschedule with an explanation, with confirmation on screen and a retained program history. Booking email/SMS, calendar invitations, and organizer notifications remain planned, not implemented.

One week before participating, send email and consented SMS reminders with a confirmation link. Organizers can see acknowledgments, delivery failures, and upcoming programs. Bookings made within the reminder window receive their booking confirmation immediately, not a redundant overdue reminder.

## Program Boundaries and Scheduling

A participant has one identity and separate program memberships. Organizers see only memberships and booking history for programs they manage. Private contacts and participant rosters remain restricted. Program detail pages are public through `/sessions` slugs, retained slugs, and database IDs, without legacy root shortcuts: visitors see only name, address, regular schedule, and the calendar. Confirmed upcoming bookings expose only active participants' current `public_name` and opted-in Instagram helpers. Inactive accounts remain booked without exposing identity. Canceled/rescheduled ledger history, contact information, pay, participant instructions, invitation lists, pause notes, and internal schedule explanations are not public. Closed public dates use a generic explanation; one-off times remain visible without their internal reason.

The visible calendar grid also shows past scheduled programs, including programs without a booked participant. Past non-program days are entirely blank. Retained completed bookings within that grid show their saved time and only the participant's current public name/opted-in Instagram, preserving private identity and inactive-account anonymity; cancellation/rescheduling history, explanations, contacts, and ledger access remain private. Public month navigation still begins at the current program-local month rather than exposing an unrestricted archive.

Venue coordinators inherit access to all programs at their venue through `VenueMembership`. A `ProgramMembership` grants local `program_coordinator` and/or `participant` access, without changing global account roles. Admins invite or promote venue coordinators; admins and venue coordinators invite or promote program coordinators using an email, never a global user directory. Registered active accounts require an explicit management-role confirmation; existing memberships and booking grants are preserved. Unique memberships and atomic role additions/removals preserve concurrent grants and retained records. Revocation removes the specific capability, with any independently granted or inherited access retained.

`CoordinatorInvitation` records grant exactly one venue or program coordinator role, never a system admin or participant role. They use the same hashed, expiring, revocable, single-use token and optional-email policy as participant invitations. A specified recipient email restricts registration and existing-account acceptance to that address; a blank email generates a private bearer link and sends no email. Registration, token consumption, and membership grant commit together in a replica-set transaction, with a fresh existing-account read and normalized email comparison. Wrong signed-in accounts see an explicit logout/account-switch action that preserves the link. The sender must still be active and authorized to delegate the target when the link is accepted. Optional email delivery follows existing invitation delivery configuration; failures retain the private shareable link. Coordinator invitation lists, recipient addresses, and revocation are restricted to system admins for venues and the parent venue's managers for programs.

Program lists and all private management/booking routes retain authenticated, program-scoped authorization; public detail visibility never grants membership or permission. Members retain their own booking information, pay, and participant instructions, while managers retain program history and controls. Schedule access does not permit user administration or organizer role assignment. Only system admins see the global active-user assignment selector; parent venue managers see their program coordinators' emails on scoped management pages. Assigned schedule organizers can invite participants and see their program's invitation/booking history; participants cannot see other participants' private contacts or history. Participants change or cancel only their own upcoming bookings. Invitation-email links still require sign-in and validate membership before returning to the program. Program hostname routing remains future work.

`mongoid-slug` generates unique venue and program slugs during normal saves from the name or an optional custom value. Generated links use `/venues/:slug` and `/sessions/:slug`, without root shortcuts. Nested organizer/invitation/booking routes accept program slugs but remain private and program-scoped. Slug history and original MongoDB IDs continue to resolve, and reserved application paths receive suffixes instead of being shadowed. Blank custom values follow name changes; explicit custom values remain stable. Production startup creates the unique sparse slug indexes without a slug backfill.

Each program stores name, address, IANA time zone, decimal pay in USD, instructions, available weekdays, a regular start time, an optional end time, and a positive booking horizon in months. New programs default to `UTC`, zero pay, Mondays at 9 AM, no end time, and six months. Existing configured values and saved booking instants are not rewritten. Pay is informational, not payment processing.

The usual event times are the program's editable `start_time` and optional `end_time`. An earlier end time means the following day; equal times are invalid. A shared view helper displays regular weekdays, times, nominal duration, and program time zone on program lists, details, calendar headers, management pages, personal invitation pages, and invitation emails. Calendars show each date's actual time and elapsed duration, including exceptions and daylight-saving transitions; booking summaries, cancellation forms, and participant rosters use saved booking times rather than substituting the current usual times.

The server-rendered month calendar uses a program-local, inclusive calendar-month booking horizon and displays each booking's start time. Past dates, unavailable weekdays, closed/occupied days, dates outside the booking window, and additional dates while already scheduled remain unavailable for personal booking. Month navigation is bounded and retains rescheduling context. A dependency-free JavaScript enhancement fetches the page and replaces only the calendar, preserving explanation drafts and supporting browser Back/Forward. A server-derived viewer/access context forces full-page navigation when the user or role changes, including program expiry or membership revocation, so old private information is removed. Superseded requests are canceled, focus moves to the updated month without scrolling, and ordinary links remain the fallback when JavaScript is unavailable or navigation fails. Nonexistent daylight-saving local times are rejected; repeated local times resolve using Rails' daylight-saving preference.

Calendar display shows only the date for ordinary unscheduled days, "Past" for unbooked past dates, and "Future" beyond the booking horizon, with longer reasons outside the badge. Authorized organizers can select an unscheduled date number to edit it; guests and participants cannot. Guests and participants also see a date-only Future placeholder for future dates outside the displayed month. Authorized program organizers instead see those dates' actual schedules and scoped Edit Day/Edit Booking/Schedule Participant controls, still respecting the booking window and server-side authorization. Past dates never offer booking/editing controls; historical schedule exceptions are loaded for the visible grid, while the separate upcoming-booking query continues to govern personal booking permission and summaries.

Each program owns its invitations, roster, recurring weekdays/start time, dated schedule exceptions, time zone, address, pay, instructions, and configurable booking horizon. Default availability is the next six months, opened automatically. System admins edit the regular start time in program settings. Both admins and assigned schedule organizers can manage dated exceptions without gaining general program administration.

`ProgramScheduleException` has a unique program/date index, an open/closed/regular mode, an open-date start time and optional end time, and a required explanation of at most 200 characters. Open overrides weekday availability and both times; closed blocks the date; regular restores the recurring rule without deleting the exception record. `mongoid-history` retains exception versions and actors. Past/out-of-window exception edits are rejected. Closing an occupied booking, including restoring a normally unavailable weekday, cancels its booking with that explanation and releases its claim in the same transaction. Time changes retain the booking and append attributed old/new UTC times. Regular time edits update upcoming regular bookings and their claims but preserve dated overrides; no notification email is sent.

Booking mutations, dated exceptions, and program settings share a transactional program revision write. This serializes overlapping operations and forces conflicting transactions to retry with fresh program/exception state, preventing bookings from slipping through a concurrent closure or retaining a stale start time. Invalid changes and failed claim/time writes roll back settings, exceptions, bookings, and audit entries together. Administrative scripts that change schedules must use these mutation services, not direct updates.

Programs independently select which genders cannot repeat in immediately adjacent scheduled programs; all are unrestricted by default. Both the preceding and following scheduled program are checked, including completed preceding bookings. An unbooked scheduled program breaks the sequence rather than looking farther for a booked participant. Dated openings participate, while closures and nonexistent daylight-saving start times are skipped. Canceled/rescheduled records and other programs do not count, and a personal reschedule excludes the reservation being replaced. The participant's calendar and transactional mutations share the same rule, using current profile genders without publishing them. Later rule, schedule, or gender edits do not automatically cancel existing reservations. Assigned organizers can explicitly override a consecutive-gender conflict with the booking explanation; its reason, creating actor, and creation time remain on the retained replacement/new booking, visible only in manager history. Missing gender selections cannot be overridden.

A participant may have one upcoming booking per program and a day may have one participant. `Booking` stores the retained history in `bookings`: original date, program/user, time-zone snapshot, UTC start, optional scheduled end, expiry, time-change entries, status, transition explanation/actor/time, and a previous-booking link on replacements. A configured end determines completion and claim expiry; without one, expiry remains the saved local end of day. Older bookings without a start instant display the original 6:30 PM in their saved time zone, and existing bookings keep their previous expiry until an applicable schedule edit. Cancellation closes the record; rescheduling closes the original and creates a linked replacement. Application deletion entry points are guarded and there is no booking deletion route.

`BookingClaim` contains disposable active pointers, with database-unique program/date and program/user indexes. A replica-set transaction commits each booking, cancellation, or reschedule with its claim update, so a failed replacement cannot lose the original reservation or leave a ledger record. Rescheduling updates the existing claim rather than trying to reuse a deleted unique key inside a transaction. Expired claims are removed before booking mutations; retained past bookings display Completed from their saved UTC expiry. Rollover requires no background job. Historical bookings are never removed by expiry or cancellation, and program setting changes do not rewrite them.

Calculate weekly programs and the one-week reminder in the program's local calendar, then store instants in UTC. Cover daylight saving changes. Cancellation and rescheduling must invalidate obsolete pending messages and update calendar invitations. Reminder delivery requires a durable worker, idempotent scheduling, retries, opt-out handling, and acknowledgment tracking; a successful provider request is not proof of recipient delivery.

Attendance confirmation opens at local midnight seven calendar days before the saved booking date and closes at the booking's saved start instant. It is separate from the reservation's existing `confirmed` status. Participants confirm through **I'll be there!** and cannot clear that confirmation. Before the inclusive five-calendar-day rescheduling cutoff, **I can no longer make it.** opens the existing explanation-and-date workflow. An unconfirmed booking at or beyond the cutoff shows an urgent organizer-contact notice to its participant and an overdue warning to authorized managers on the calendar, history, roster, and editor. Positive confirmation is public without exposing private identity; overdue state, contact details, and change history are private. Calendar-day calculations use the booking's saved program time zone, including across daylight saving and later program-settings changes. A program without listed active organizers directs the participant to contact the program. Cancellation remains available and retains the booking history.

`attendance_confirmed_at` and `attendance_confirmed_by_id` store the latest confirmation metadata; append-only `attendance_changes` retain each transition, actor, time, and explanation. The persisted reservation state remains `confirmed` independently of attendance; display combines the two without changing booking or mutation rules. Canceled, rescheduled, and completed bookings show only their terminal label, retaining previous attendance confirmation in the historical explanation rather than another badge. Personal confirmation and organizer mutations use the same retrying program schedule lock as bookings and recheck fresh authorization and booking state inside it. Repeated personal confirmations are idempotent. Date/participant replacements retain the original confirmation history; participant-initiated replacements start unconfirmed. Assigned organizers and system admins can create, reassign, reschedule, cancel, and set/clear attendance for upcoming bookings at managed programs, without changing unrelated account or program-settings permissions. They explicitly choose the resulting attendance state, and replacements update the existing unique claim atomically. New bookings retain their creating actor. No attendance email or automated reminder is sent. Calendar navigation reloads the full page if scheduling or attendance context changes, removing stale summaries and controls.

If another participant takes a date after a calendar or organizer form was opened, recheck its claim inside the program schedule transaction and show a friendly date-taken message instead of relying on a duplicate-key error. The participant's refreshed calendar stays on the submitted month; failed rescheduling retains the original reservation and explanation draft. Organizer replacements exclude their original claim so same-date participant reassignment remains possible. Unique indexes remain the final safeguard.

Booking attendance, time, cancellation, and replacement writes use an atomic compare-and-increment `lock_version` alongside their state/history update. Existing records without the field start at revision zero. Participant confirmation/change/cancellation and organizer edit/cancellation forms carry the displayed revision; missing, malformed, or stale revisions cannot mutate a booking. Transactions recheck the original submitted revision on every retry instead of applying stale user intent to newer state. A conflict redirects to the latest program details for review, never a stale form with a refreshed token. Replaced/canceled bookings are detected within authorized scope, so old submissions receive a friendly conflict while foreign bookings remain hidden.

Repeated positive participant confirmations are safe no-ops without duplicate history, but an old confirmation cannot undo a later organizer clear. Schedule-driven time changes also advance booking revisions. Existing program transactions still commit claims, replacement records, cancellation history, attendance changes, and schedule updates together; a failed transaction rolls back its revision increments as well.

## Booking Permission and Participant Pauses

Program participant membership does not automatically grant unlimited repeat bookings. Membership stores the booking invitation time and inviting actor, plus a separate paused flag and short private explanation. The first accepted participant role grants one booking cycle; accepting another registration invitation for an existing participant never renews permission or bypasses a pause. A grant remains usable through cancellation/rescheduling and is exhausted when a confirmed booking completes at its saved expiry. Past-start bookings cannot receive new bookings.

System admins and assigned program organizers manage individual or bulk invitations from the program's Participants page. Bulk delivery selects only active accounts at that program without a pause or upcoming booking. Permission opens immediately. Grants and pause/resume changes share the program schedule transaction lock with booking mutations, and booking/rescheduling rechecks permission inside each transaction attempt. Pauses retain existing bookings and cancellation rights; resume restores only unused permission, never a fresh cycle after completion. Changes are audited through `mongoid-history` on the membership, and pause explanations are not exposed to participants or request logs.

Email is sent once after each successful grant transaction, outside retry blocks. Delivery failures or unavailable SMTP leave access enabled and are reported for explicit follow-up; bulk results report sent, failed, and skipped counts. Email links preserve the intended program across login but resolve it through the signed-in user's authorized program scope. No token grants access by itself, no delayed invitation release is implemented, and no background scheduler is introduced.

The private Participants roster shows 25 participants per page with stable ordering, program-wide counts, and compact invitation/resume controls; pause forms and notes expand on demand. Counts group inactive accounts first, then paused participants, then booked participants, with remaining participants available for invitations, including previously invited participants without upcoming bookings. Bulk invitations always cover every page and recheck availability when granting access. Individual and bulk actions retain the current page.

Legacy memberships without an invitation timestamp may finish or cancel an existing booking cycle using the latest booking's creation time as a compatibility baseline. Completed cycles do not renew, and a legacy participant with no bookings requires an explicit invitation. Cancellation history remains usable rather than expiring permission on the canceled date. No bulk permission backfill is performed.

## Architecture and Deployment

Use Rails 8.1 with server-rendered views, Mongoid 9.1, and MongoDB 8.0. Ruby 4.0.9 is the stable runtime selected at scaffold creation. Test one MongoDB version, 8.0, to match the deployment target rather than maintaining a server-version compatibility matrix. Commit `Gemfile.lock` because this is an application, not a published gem.

Use Rails and Mongoid public APIs. Do not configure Active Record, Solid Queue, or another SQL-backed component. The scaffold retains ActiveJob's in-process adapter solely as framework setup; a durable MongoDB-compatible worker and notification providers will be selected and tested in the implementation phase. No background reminders are promised by this scaffold.

The Dockerfile explicitly selects runtime files, installs production dependencies, precompiles assets without live services, creates declared indexes at container startup, and runs Puma as a non-root user. The package check runs the built image against its own MongoDB 8.0 container and verifies first-user registration, compiled CSS, and liveness. CI reuses Docker build layers, runs the same smoke checks against the already built image without installing host application gems, and overlaps test database/image-library setup. Only superseded PR runs are canceled; default-branch checks are preserved. Application tests exercise real MongoDB persistence and concurrent bootstrap, reset, email-confirmation, and organizer-assignment claims. Deployment is intended for DigitalOcean App Platform with managed MongoDB and an HTTPS-terminating proxy, but no infrastructure or credentials are provisioned.

Production requires `MONGODB_URI` and a deployment-supplied `SECRET_KEY_BASE`. `APP_HOST` defaults to `localhost`; external deployments must set their own hostname. Production requests are host-restricted except for `/up`. Local test configuration uses a separate URI and a test-only database-name guard. Filter email, phone, passwords, and authentication tokens from logs. Email password recovery uses SMTP; participant notifications remain unimplemented.

Optional `newrelic_rpm` monitoring uses `NEW_RELIC_LICENSE_KEY` and `NEW_RELIC_APP_NAME` (default `Posebook`), following the Slack bots' environment-variable setup. Production starts the agent only with a license; development and tests disable it. Rails instrumentation reports unhandled failures, and explicit `NewRelic::Agent.notice_error` calls report handled SMTP and photo-storage failures without changing their existing responses or booking grants. Disable request/custom attributes, MongoDB query capture, exception messages, log forwarding, and browser injection; report exception classes and stack traces, not contacts, authentication links, profile fields, uploaded images, or private database values. No additional service credentials are required to build, test, or boot without monitoring.

## Delivery Scope

Implementation proceeds through focused PRs. SMS consent, phone verification, opt-outs, and invitation expiry are required before the corresponding public messaging functionality launches.

Single-use, 30-day personal program invitations support private links and optional transactional SMTP delivery. A specified email restricts acceptance to that address, including already-issued links. Without an email, they remain private bearer links that one chosen recipient can accept with any account. Blank-email invitations send no email even if delivery was selected. Registration fills in a specified email and makes it read-only; the server independently rejects mismatches without creating accounts, consuming tokens, or granting access. Wrong signed-in accounts must sign out and use the invited address, with the link retained across logout and login. Only digests persist; GET does not consume them. An explicit authenticated acceptance or invited registration atomically creates the account if needed, consumes the invitation, and adds a participant role without dropping existing membership roles. Failed registration or a concurrent losing claim leaves no orphan account. Participants see their assigned programs, not organizer controls or other participants' contacts. Automated booking notifications and reminders remain future work.

Invitation and booking transactions require a MongoDB replica set; development and CI use a single MongoDB 8.0 replica-set node. Production packaging verifies an actual transaction rollback. Optional invitation-email failure preserves the private link for manual delivery; missing SMTP never pretends email was sent. Normal public registration remains closed.

Version one excludes payments, attendee registration, and public participant directories.
